# Cross-platform alternatives for the TV-first IPTV app

Research date: 2026-10-04. This compares alternatives with the provisional Kotlin, Compose for TV, and Media3 stack. Scope: Google/Android TV first, Android-based Fire OS second; Apple TV and Vega later. Sources establish documented capabilities and maintenance status. No app, provider stream, build, or physical device was tested.

## React Native TV: the strongest alternative

**Documented facts.** React Native renders native platform components. Apple TV and Android TV support is maintained outside core in the community `react-native-tvos` fork. Its TV APIs include native focus/press events, focus destinations, restoration through `TVFocusGuideView.autoFocus`, directional focus trapping, and TV-aware virtualization that also applies to `FlatList`. These directly address remote navigation rather than requiring a touch interface to be adapted unaided. [React Native components](https://reactnative.dev/docs/intro-react-native-components), [React Native TV implementation](https://github.com/react-native-tvos/react-native-tvos)

Core `FlatList` documents windowed rendering, external state requirements when rows unmount, and possible temporary blank regions when scrolling outpaces rendering. **Judgment:** a large channel lineup is feasible, but correct identity, focus restoration, and render-window tuning are application responsibilities. Neither the API nor a framework label proves sustained D-pad behavior while video plays. [FlatList contract](https://reactnative.dev/docs/flatlist)

Amazon explicitly documents React Native TV for Fire OS with Android builds. Its Android compatibility remains conditional on APIs/services and device versions. The TV fork is actively releasing: GitHub marks 0.87.1-1, released September 18, as latest stable, with a 0.88 release candidate on September 30. This is maintained TV work, with its own upgrade stream to track. [Amazon React Native guide](https://developer.amazon.com/docs/fire-tv/get-started-with-react-native.html), [Fire OS compatibility](https://developer.amazon.com/docs/fire-tv/fire-os-overview.html), [TV fork releases](https://github.com/react-native-tvos/react-native-tvos/releases)

Expo's TV guide lists SQLite, AsyncStorage, SecureStore, Video, FlashList, and React Navigation as supported. It requires the React Native TV version to match the selected Expo SDK. **Judgment:** local favorites/history, saved browsing state, and TV text entry have credible building blocks; secure setup and restoration semantics still need design and verification. [Expo TV support and version alignment](https://docs.expo.dev/guides/building-for-tv/)

The media path can use native engines: `react-native-video` v6 documents ExoPlayer on Android and AVPlayer on tvOS. Current v7 is Beta/active development; its introduction lists tvOS support, while its repository marks TV support TODO. These first-party claims conflict; they do not prove v7 cannot run on TV. V6 remains maintained. Expo Video is another candidate with Android/tvOS APIs, live-stream identification, track selection, source replacement, and playback events. Qualify a specific wrapper/version. [Video v6 engines](https://docs.thewidlarzgroup.com/react-native-video/docs/v6/intro/), [V7 introduction](https://docs.thewidlarzgroup.com/react-native-video/docs/v7/fundamentals/intro/), [Video project status](https://github.com/TheWidlarzGroup/react-native-video), [Expo Video API](https://docs.expo.dev/versions/latest/sdk/video/)

**Strongest reason to choose it:** if Apple TV becomes a committed near-term delivery target, or the implementers already have substantial React/TypeScript expertise, sharing TV screens and domain logic could outweigh the wrapper and fork maintenance. The live-only scope, without DVR or a custom temporary buffer, avoids some specialized media work. That is a scope-based judgment, not evidence of faster delivery or equal playback reliability.

## Flutter: viable building blocks, weaker TV-specific support evidence

**Documented facts.** Flutter's supported-platform matrix lists Android, but not tvOS. Its Android-team TV umbrella issue remains open and explicitly identifies gaps in input, focus, navigation, tooling, documentation, and tests, while acknowledging that generic Android Flutter apps run on Android TV. Individual linked bugs do not establish that every current TV build fails. [Flutter support matrix](https://docs.flutter.dev/reference/supported-platforms), [Android TV support tracker](https://github.com/flutter/flutter/issues/180542)

Flutter provides programmable focus scopes, directional movement, and custom traversal policies. `ListView.builder` builds visible children on demand and exposes index mapping to avoid state loss after reordering. Navigator/Router supply navigation, and the documented SQLite path supplies local persistence. These are substantive capabilities for the required UI, not evidence that remote-input edge cases are already solved. [Focus system](https://docs.flutter.dev/ui/interactivity/focus), [Lazy lists](https://api.flutter.dev/flutter/widgets/ListView/ListView.builder.html), [Navigation](https://docs.flutter.dev/ui/navigation), [SQLite](https://docs.flutter.dev/cookbook/persistence/sqlite)

Flutter's official `video_player` uses ExoPlayer on Android and AVPlayer on Apple platforms it supports; its Android changelog confirms Media3 integration. The community `media_kit` offers a different libmpv-based path through Dart FFI. Neither selects a universally superior IPTV engine: stream compatibility, rendering surfaces, audio tracks, and lifecycle behavior need hardware evidence. [Video player](https://pub.dev/packages/video_player), [Android implementation history](https://pub.dev/packages/video_player_android/changelog), [media_kit architecture](https://github.com/media-kit/media-kit#implementation)

The community `flutter-tvos` project supplies a separate CLI/engine and requires explicit tvOS plugin implementations; ordinary iOS plugin support does not automatically transfer. **Judgment:** Flutter becomes more attractive with established Dart expertise or a proven TV component/player base. Starting from zero, its general cross-platform reach does not yet compensate for the documented TV-specific gaps in this TV-first project. [Community tvOS toolchain](https://github.com/fluttertv/flutter-tvos)

## Later portability and the decision boundary

Vega is a separate Amazon React Native runtime. Pure JavaScript/TypeScript code can often transfer, but Android/iOS native libraries need Vega ports and media uses Vega's APIs. No verified Flutter-to-Vega path was established here. Do not equate ordinary Android or Linux support with Vega compatibility. [Vega library boundaries](https://developer.amazon.com/docs/vega-api/0.24/porting-libraries)

Kotlin Multiplatform can share domain logic while retaining native interfaces. Official core tvOS support is Beta; official Compose Multiplatform UI support does not list tvOS. **Judgment:** shared provider/catalog/personalization rules remain an option alongside native Android now and native tvOS later; implementing KMP immediately is not required to preserve that boundary. [KMP sharing options](https://kotlinlang.org/docs/multiplatform/faq.html), [Platform/UI support](https://kotlinlang.org/docs/multiplatform/supported-platforms.html)

**Current judgment:** native Android remains a defensible provisional choice because the first two selected targets share Android foundations. React Native TV deserves a real comparison if earlier tvOS delivery or team expertise changes that tradeoff. Flutter needs stronger project-specific evidence. Missing EPG handling, local persistence, and a phone setup webpage do not themselves demand a shared TV UI framework.

What could change the recommendation: demonstrate equivalent focus/Back restoration during fast channel-list navigation, sustained playback under overlays, channel switching and recovery, TV text entry, and retained personalization on the user's Google TV and a representative Fire OS device. Framework documentation cannot establish the winner on those behaviors.
